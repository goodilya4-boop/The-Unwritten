# Architecture

## Platform

- Minecraft: 1.21.1
- Loader: NeoForge
- Java: 21
- Build system: Gradle
- Mappings: Parchment

## Mod

- Mod ID: the_unwritten
- Mod name: The Unwritten
- Base package: com.theunwritten

## Core principles

1. Игровая логика не должна зависеть от клиентского рендера.
2. Постоянные данные персонажа хранятся отдельно от вычисляемых характеристик.
3. Системы должны иметь минимальное количество прямых зависимостей друг от друга.
4. Игровые правила сначала проектируются, затем реализуются.
5. Каждая крупная система должна иметь собственную документацию.

## Character data

- Attributes хранит базовые STR, DEX, END, INT, WIL и PER.
- CharacterAttributeAccess представляет эффективные значения атрибутов с учётом runtime-модификаторов.
- CharacterStats вычисляет производные характеристики из эффективных атрибутов.
- CharacterResources хранит текущие ресурсы персонажа.
- Potential задаёт мягкий ориентир развития, а не жёсткий предел.
- CharacterData объединяет постоянное состояние персонажа и runtime-доступ к атрибутам.

## Attribute modifiers

Используется одна каноническая модель AttributeModifier.

Модификатор имеет стабильный id, целевой атрибут, amount, операцию и ResourceLocation source.

Порядок вычисления фиксирован:

Base → ADDITION → MULTIPLY_BASE → MULTIPLY_TOTAL

Формула:

effective = (base + additions + base × sum(multiplyBase)) × (1 + sum(multiplyTotal))

Мультипликативные значения являются дельтами: 0.25 означает +25%.

Модификаторы одной операции сначала суммируются, поэтому результат не зависит от порядка их регистрации.

source идентифицирует владельца набора модификаторов. Для runtime-экипировки система нормализует source к идентификатору конкретного equipment slot. Поэтому снятие и повторное надевание предмета идемпотентно и не требует хранения runtime-модификаторов в NBT.

AttributeAccess.addModifier гарантирует уникальность пары (source, id): повторная регистрация того же идентификатора заменяет предыдущую запись.

## Item data components

Компонент attribute_modifiers хранит модификаторы, предоставляемые предметом. Он является декларацией данных предмета, а не механизмом экипировки.

EquipmentAttributeLifecycle:

1. получает LivingEquipmentChangeEvent;
2. удаляет runtime-модификаторы данного slot;
3. читает attribute_modifiers текущего ItemStack;
4. применяет их с source, принадлежащим этому slot;
5. пересчитывает максимумы ресурсов.

NeoForge сообщает об изменениях экипировки также при первоначальном появлении сущности и её клонировании, поэтому отдельная сериализация runtime-состояния экипировки не требуется.

## Persistence boundary

Сохраняются базовые Attributes, Potential и текущие/максимальные Resources.

Runtime AttributeModifier из экипировки не является самостоятельным source of truth. После загрузки они восстанавливаются из фактически экипированных предметов.

## Testing

Тесты foundation проверяют формулу модификаторов, удаление по source, замену по (source, id), возможность использовать одинаковые id в разных source и reconciliation жизненного цикла экипировки.

Для проверки интеграции существует конкретный Training Charm. Он хранит attribute_modifiers как Data Component и предоставляет +5 WIL при экипировке. Его source из данных предмета не считается runtime-источником: при применении lifecycle заменяет source на идентификатор equipment slot.
